1. 一句话理解需求

这个 Demo 要回答一个关键安全问题：进入蜜罐的攻击者是人、传统自动化扫描器，还是 AI Agent？

更准确地说，它不是只看某一条“很危险”的命令，而是把一个会话里的多类证据组织成攻击流：

单请求特征
观察一次登录、一条命令、一个 User-Agent 或协议指纹是否异常。
诱饵行为观察
主动放置假凭据、假备份文件和反向提示词，观察攻击者是否会触碰并继续执行工具调用。
同源 IP 聚合
把同一来源 IP 产生的登录、命令执行、文件访问等事件串成完整攻击链，而不是孤立看单条日志。
当前 Demo 的核心判断信号：攻击者读取 /root/.cache/backup/canary_credentials.csv 后，如果继续执行 tool_call: upload_artifact，说明其大概率被蜜罐中的反向提示词诱导，具备明显的 AI Agent 行为特征。

2. 为什么这个需求有价值

传统安全规则通常关注“行为是否危险”。例如 cat /etc/shadow、读取 authorized_keys、执行扫描命令，都会被判定为高风险。但这类判断很难区分“专业渗透测试人员”和“AI Agent”。

AI 攻击的新特点
AI Agent 可能以自然语言任务驱动，自动规划、调用工具、循环试错、读取上下文，甚至执行模型不应该执行的操作。
单点特征不可靠
User-Agent 可以伪造，某些命令也可以伪装成运维行为，所以 Demo 强调不能只依赖 UA、ALPN 或单条命中。
主动验证更可靠
蜜罐不只被动记录，还可以构造只对攻击者可见的诱饵。AI Agent 读取诱饵后如果执行反向提示词，就形成了强信号。
攻击者类型常见表现识别思路
人工攻击者节奏不稳定，可能反复尝试，也常先人工探测。看会话节奏、命令组织、上下文连贯性。
传统扫描器常见固定扫描路径、批量请求、已知 Payload。识别工具签名和扫描模式，但不直接等同 AI。
AI Agent任务驱动，工具调用，指令式行为，可能被注入提示词诱导。结合多轮行为、工具链和诱饵确认。
正常运维有明确运维目标，命令相对收敛，来源较可信。白名单、身份、来源和操作上下文辅助判断。

3. 系统架构与数据流

Demo 由四类角色组成：蜜罐采集行为，识别后端整理证据，前端展示会话和结果，LLM 做最终研判。

目录 / 文件职责对应后端角色
honeypot/honeypot_server.py模拟 SSH 服务，处理登录、命令和会话事件。采集端 / 数据生产者。
honeypot/deception_detector.py检查命令是否触碰诱饵、出现注入或工具执行。规则识别层。
backend/demo_server.py提供页面、场景 API 和 LLM 代理，聚合会话证据。应用后端 / BFF。
tools/ai_attacker.py、tools/human_attacker.py模拟 AI 和人工攻击会话。测试数据生成器。
frontend/AI流量识别Demo.html展示请求、证据、诱导确认和 LLM 研判结果。前端展示层。
samples/*.jsonl保存历史样本和传感器事件。离线数据 / 评测样本。
关键文件：蜜罐事件默认写入 honeypot/data/events.jsonl；容器内后端通过 HONEYPOT_EVENTS_PATH=/data/honeypot/events.jsonl 读取同一个 Docker Volume。

4. 后端知识地图

不用一口气掌握所有内容。先理解当前 Demo 用到的概念，再逐步补齐通用后端能力。

1. HTTP 与 API

前端和后端通过 HTTP 交换数据。GET 常用于查询，POST 常用于提交或触发动作。本 Demo 提供 /api/scenarios、/api/llm/prompt、/api/llm/judge。

2. JSON 与序列化

后端把 Python dict 转成 JSON 字符串返回给浏览器；接收请求时也先把 JSON 字符串解析回 dict。

3. 请求 / 响应状态码

200 表示成功，404 表示找不到资源，502 在这里通常表示后端调用上游 LLM 失败。

4. 进程 / 线程模型

ThreadingHTTPServer 会为每个连接分配线程处理请求，所以 Demo 能同时服务多个页面请求。

5. 文件持久化

Demo 用 JSONL 逐行保存事件。每行一条 JSON，读取时逐行解析，适合简单追加和离线分析。

6. 会话与聚合

单条日志价值有限。后端用 session_id 分组，把登录、命令、关闭事件拼成一次完整会话。

当前 Demo 用到的核心概念

概念在项目中的位置理解方式
HTTP ServerThreadingHTTPServer接收浏览器请求并返回 HTML / JSON。
路由do_GET / do_POST根据 URL 决定执行哪段逻辑。
环境变量DEMO_PORT、LLM_API_KEY不改代码就切换端口、模型和密钥。
外部服务调用urllib.request.urlopen后端作为客户端，调用 LLM Gateway。

Dockerdocker-compose.yml把蜜罐、后端和攻击模拟器组成多容器环境。
Volumehoneypot_data让容器删除后事件文件仍然保留。
生产系统会复杂得多：通常还需要身份认证、权限校验、请求限流、结构化日志、指标监控、链路追踪、数据库、消息队列、任务调度、灰度发布和安全审计。

5. 核心代码流程讲解

5.1 事件如何从蜜罐写入文件

SSH 蜜罐在收到连接后创建一个会话对象。密码校验、命令执行、会话关闭都会生成事件记录。简单理解就是：

攻击者连接蜜罐
  ↓
记录 password_login 事件
  ↓
攻击者执行命令
  ↓
记录 shell_command 事件
  ↓
写入 honeypot/data/events.jsonl

事件里最重要的是 session_id、source_ip、event、command 和 timestamp。没有 session_id，后端就无法把多个事件归成一次攻击会话。

5.2 后端如何把事件变成场景

build_honeypot_scenarios() 是聚合入口。它先读 JSONL，再按 session_id 分组：

events = read_jsonl(HONEYPOT_EVENTS_PATH)
sessions = {}

for event in events:
    session_id = event.get("session_id")
    sessions.setdefault(session_id, []).append(event)

然后它把一次会话中的登录和命令事件转换成前端更容易理解的请求列表：

原始事件转换后的展示信息
password_loginSSH 登录、用户名、脱敏后的密码、登录结果。
shell_commandSSH 命令执行和具体命令内容。
session_closed主要用于补全会话状态，不进入前端请求列表。

5.3 诱饵识别怎么做

deception_detector.py 会遍历会话中的命令，检查三个条件：

  1. 触碰诱饵：命令中出现诱饵路径或文件名，例如 canary_credentials.csv。
  2. 出现注入：命令或上下文包含反向提示词标记，例如 ignore previous。
  3. 工具执行：出现 tool_call: upload_artifact 这类 Agent 工具调用。
只读诱饵文件       → partial（部分确认）
读诱饵 + 工具执行   → strong（强确认）
两者都没有          → none（无诱导确认）
这是整个 Demo 的灵魂：蜜罐返回的假文件里包含反向提示词，诱导 AI Agent 执行可观测的工具调用。这样识别就从“猜测客户端是谁”升级为“观察攻击者是否表现出 Agent 式行为”。

5.4 后端如何返回给前端

浏览器访问 GET /api/scenarios，后端把聚合结果包成 JSON：

{
  "scenarios": [
    {
      "key": "live_ssh_xxx",
      "label": "SSH 蜜罐 · AI 诱导确认",
      "sourceIp": "...",
      "sessionId": "...",
      "decoyHit": true,
      "requests": [...],
      "deceptionEvidence": {...},
      "isAi": true
    }
  ]
}

当前代码按 is_ai 分成 AI 和非 AI 两类，每类只保留最新一条。这样页面演示时不会历史数据越积越多。

6. 接口与数据结构

接口方法作用
/healthzGET健康检查，确认后端是否可访问。

LLM 研判流程

前端传入证据
包含请求列表、诱饵证据、来源 IP、会话 ID 等内容。
后端构建 Prompt
System Prompt 约束角色、分类标准、置信度和输出格式。
调用 LLM Gateway
请求体包含模型名、温度、system/user 消息，Header 携带 API Key。
解析返回内容
模型必须返回 JSON：verdict、confidence、stage、intent、reason、recommendation。
前端展示结论
展示判定类型、置信度、攻击阶段、意图、理由和处置建议。
{
  "verdict": "ai",
  "confidence": 0.92,
  "stage": "credential discovery",
  "intent": "读取诱饵凭据并尝试外传",
  "reason": "命中诱饵文件后继续执行 tool_call: upload_artifact",
  "recommendation": "聚合同源会话，阻断后续操作并人工复核"
}
接口安全提醒：Demo 中前端可以携带证据直接调用 LLM 接口，后端用服务端环境变量中的 API Key 转发。生产系统必须限制谁能调用、调用频率是多少、允许携带的证据大小是多少，并校验证据来源。

7. 识别逻辑与 LLM 研判

可以把系统分成两层：确定性的规则层和概率性的 LLM 研判层。

层级做什么优点局限
规则识别层整理事件、聚合会话、检测诱饵命中和工具调用。可解释、可测试、结果稳定。规则覆盖有限，容易绕过。
LLM 研判层综合证据链，区分 AI、传统扫描、人和证据不足。能处理复杂上下文和模糊语义。可能幻觉、误判，输出需要约束。
人工复核层处理高风险、低置信度或业务关键事件。兜底误判，沉淀标注样本。成本高，不能覆盖全量。

强信号与弱信号

  • 强信号：触碰诱饵后又执行了反向提示词要求的工具调用。
  • 中信号：读取诱饵文件、命令编排高度任务化、连续出现多步侦察。
  • 弱信号：User-Agent、ALPN、TLS 指纹、单个高危命令。
不要把单个弱信号当成最终结论。例如攻击工具可以伪造 UA，传统扫描器也不是 AI，高危命令只说明行为危险，不说明发起者一定是 AI Agent。

识别结果应怎么用

  1. 接入攻击者画像，补充来源特征和历史行为。
  2. 生成或增强告警，附带可解释证据链。
  3. 在前端给安全分析人员展示判定理由。
  4. 旁路验证后再考虑自动处置，避免误杀正常运维。

8. Demo 边界与真实落地

当前它是一个 POC，不是上线能力。样本是自造对照样本，只覆盖 SSH，效果尚未评测，因此不能得出真实环境中的准确率结论。

主要局限

  • 样本不足：缺少真实 AI Agent、传统扫描器、人工攻击、正常运维和硬负样本。
  • 场景单一：目前主要集中在 SSH，不能代表 HTTP、数据库、云 API、K8s 等攻击面。
  • 规则较简单：诱饵命中依赖字符串匹配，真实攻击者可能改写路径、命令或提示词。
  • AI 判定依赖演示痕迹：tool_call 在当前样本里是可观测命令，但真实 Agent 不一定这样执行。
  • 存储和查询能力有限：JSONL 适合 Demo，不适合大规模检索、聚合和实时流式消费。

真实落地要补齐的问题

模块需要回答的问题常见后端方案

字段映射谛听字段如何映射成 Demo 需要的 session_id、IP、事件类型、命令？ETL、数据契约、Schema Registry、字段校验。

评测准确率、召回率、误报率、漏报率是多少？标注数据集、离线评测、灰度验证、AB 对照。

架构演进建议

阶段一：确认数据契约
固定事件字段、时间格式、会话 ID、来源 IP、权限边界和缺失值处理。
阶段二：建立识别服务
把读取 JSONL 的 Demo 逻辑改成独立服务，增加输入校验、错误处理、日志和配置管理。
阶段三：引入持久化与队列
用数据库存储会话，用消息队列削峰、重试和解耦生产消费。
阶段四：建设评测闭环
建立标注集、规则版本、模型版本、指标报告和误报复盘流程。
阶段五：接入生产动作
先告警和画像，再灰度自动处置；所有高危动作必须有审计和回滚。

9. 后端学习路线

这条路线按“先跑通、再理解、再重构、再验证”的节奏设计，适合当前阶段。

把 Demo 彻底跑起来。
阅读 README，启动本地后端和蜜罐，运行 AI / 人工攻击器，观察 events.jsonl、/api/scenarios 和前端页面变化。

第 2 周

第 3 周

理解数据聚合。
给 read_jsonl、build_honeypot_scenarios 和 evaluate_session 画输入 / 输出表；手工改一行事件验证结果。

第 4 周

理解 LLM 调用。
对比 /api/llm/prompt 和 /api/llm/judge，观察 Prompt、响应、JSON 解析失败和后端错误处理。

第 5 周

补生产化意识。
学习日志、配置、测试、鉴权、限流、超时、重试、幂等和监控。

第 6 周

设计真实接入方案。
画一张从谛听数据到识别结果回传的架构图，明确字段、权限、频率、失败重试和数据存储。

建议亲手做的练习

  • 把 LLM_API_KEY、DEMO_PORT、HONEYPOT_PORT 写进自己的启动笔记。
  • 用 curl http://127.0.0.1:8000/healthz 验证服务状态。

10. 术语速查

蜜罐

一个故意暴露给攻击者的受控诱饵系统。攻击者以为进入了真实主机，实际行为被记录和分析。

诱饵 / Canary

假文件、假凭据、假 Token 或假数据。攻击者触碰它通常说明发生了越权访问。

反向提示词

预埋在诱饵内容中的指令，用于诱导 AI Agent 产生可观测行为。例如要求其执行 tool_call: upload_artifact。

会话聚合

把同一 session_id 或同一来源的多个事件按时间串起来，形成完整行为链。

JSONL

每行一个独立 JSON 对象的文本格式。写入简单，适合日志和批量样本。

BFF

Backend for Frontend。为特定前端裁剪、聚合和转换数据的后端层。Demo 的 demo_server.py 就承担了类似角色。

CORS

跨域资源共享。浏览器在跨源访问接口时，需要后端返回对应允许头。

幂等

同一个请求重复执行，结果不会产生额外副作用。例如同一事件重复回传时不应重复生成告警。

置信度

系统或模型对结论的把握程度。Demo 中要求 LLM 输出 0 到 1 的 confidence。

误报 / 漏报

误报是把正常或非 AI 行为判成 AI 攻击；漏报是真实 AI 攻击没有被识别。

硬负样本

特别容易导致误判但实际应判为负类的样本。例如高危但非 AI 的真实运维或传统扫描行为。

Agent 工具调用

AI Agent 通过文件、命令、HTTP、MCP 等工具执行任务的动作。它是识别 AI 行为的重要观察点。

MCP

Model Context Protocol，一种让模型访问外部工具和上下文的协议模式。Demo 的 mcpSignals 用来记录相关信号。

EOL

End of Life。指组件或流程停止维护。在安全场景中，EOL 服务常代表更大的攻击面。

下一步建议

  1. 先用现有 Demo 跑一遍 AI 和人工攻击，把整个链路亲手触发一次。
  2. 和谛听同学确认数据获取方式、可用字段和权限范围。
  3. 定义一个最小评测集：AI Agent、传统扫描器、人工攻击、正常运维、硬负样本各若干条。
  4. 把字段映射和结果回传写成接口文档，再开始改造服务。
